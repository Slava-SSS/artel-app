## 📜 ПРАВИЛА АРХИТЕКТУРЫ (КОНСТИТУЦИЯ ПРИЛОЖЕНИЯ)

**⚠️ ЭТИ ПРАВИЛА СВЯЩЕННЫ. ЕСЛИ Я НАРУШУ - СКАЖИ "ПРОЧИТАЙ PATCHES.MD"**

### 1. **БД - ИСТОЧНИК ПРАВДЫ**
- БД перезаписывается ПОЛНОСТЬЮ только при первой индексации
- При каждом запуске потом: **сравниваем файлы на диске с БД**
- НЕ СТИРАЕМ старые данные (категории, теги, историю) при переиндексации
- Если файл в БД есть - берем его данные, обновляем только что изменилось

### 2. **УНИКАЛЬНЫЙ ID ФАЙЛА**
```
ID = projectName__fileName

ПРАВИЛЬНО:  "VENDING-3__Боковая панель.dxf"
НЕПРАВИЛЬНО: "VENDING-3__bb1ac03f3722a117e7a8073fc7ee01ce"
```
- ID стабилен и основан на имени файла (которое пользователь не меняет)
- При переименовании файла - ID меняется, но история сохраняется

### 3. **ХЕШИРОВАНИЕ**
- `contentHash` = MD5 хеш СОДЕРЖИМОГО файла (для отслеживания реальных изменений)
- `hash` в БД считается ОДИН РАЗ при создании, не пересчитывается

### 4. **ИСТОРИЯ ФАЙЛОВ - ОБЯЗАТЕЛЬНА**
```javascript
{
  id: "VENDING-3__файл.cdr",
  name: "файл.cdr",
  history: [
    { action: "created", timestamp: "2026-10-09T10:00Z", ... },
    { action: "modified", timestamp: "2026-10-10T14:30Z", ... },
    { action: "renamed", from: "файл.cdr", to: "файл-новый.cdr", ... },
    { action: "deleted", timestamp: "2026-10-10T15:00Z", ... }
  ]
}
```
- История НИКОГДА не теряется
- Мягкое удаление: `deleted: true` вместо полного удаления из БД

### 5. **ПЕРЕИМЕНОВАНИЕ ФАЙЛОВ**
- ✅ Переименование ТОЛЬКО через приложение (кнопка в UI)
- ⚠️ Если переименование в проводнике → приложение попробует обнаружить (по contentHash)
- 🚫 Если не получится обнаружить → ПРЕДУПРЕЖДЕНИЕ пользователю

### 6. **WORKFLOW РАЗРАБОТКИ (КРИТИЧЕСКИ ВАЖНО!)**
```
1. АНАЛИЗИРУЮ    → Читаю код, понимаю что нужно менять

6. ФИНАЛИЗИРУЮ   → Создаю commit + tag + резервную копию
```
**НЕЛЬЗЯ:** молча менять код без анализа и рассказа!

### 7. **ДОКУМЕНТИРОВАНИЕ В PATCHES.MD**
- ДО работы: создать новый раздел версии (v0.X)
- ВО ВРЕМЯ: перемещать задачи из "НЕРЕШЕННЫЕ" в "РЕШЕННЫЕ"

### 8. **ОБСЛУЖИВАНИЕ БД**

- Если БД сломалась → всегда можно откатиться по инструкции в PATCHES.md

## Версия 0.2 (Правильная архитектура БД и истории файлов)

**Дата начала:** 10.10.2026
**Дата завершения:** 10.10.2026

### Что сделано:

1. ✅ **Переработка индексации файлов** - ГОТОВО
   - Изменил с "полной переписи" на "сравнение с БД"
   - При каждом запуске: сравниваем файлы на диске с БД
   - Сохраняем старые данные (категории, теги, описание и т.д.)
   - Отмечаем удаленные файлы как `deleted: true`

2. ✅ **Переделать ID файла** - ГОТОВО
   - С: `"VENDING-3__hash"` → На: `"VENDING-3__fileName"`
   - Миграция: все старые ID переконвертированы в новый формат
   - Пример: `VENDING-2__bb1ac03f... → VENDING-2__Боковая панель.dxf`

3. ✅ **Добавить contentHash (хеш содержимого)** - ГОТОВО
   - contentHash = MD5 от содержимого файла (не от пути!)
   - Используется для отслеживания реальных изменений
   - Обнаружение переименований по совпадению contentHash

4. ✅ **Реализовать историю файлов** - ГОТОВО
   - Массив `history` в каждом файле
   - Отслеживание: created, modified, renamed_detected, deleted, migrated

5. ✅ **Обнаружение переименований** - ГОТОВО
   - При индексации: если файл исчез, ищу его по contentHash
   - Если найду в новых файлах - это переименование
   - Обновляю историю и переношу все старые данные

6. ✅ **Функция переименования в UI** - ГОТОВО
   - Кнопка "✎" (карандаш) для переименования в обеих таблицах
   - Prompt диалог для ввода нового имени
   - Переименование на диске + обновление БД ID + история
   - IPC handler `api:renameFile`

7. ✅ **Восстановление данных из старого формата** - ГОТОВО
   - Конвертировал `links` → в `category` каждого файла
   - Все VENDING-3 категории сохранились:
     - "Фасткава 3.cdr" → "Рабочий файл" ✓
     - "Крыша.dwg" → "Чертёж" ✓
   - Добавил поля: `contentHash`, `history` для старых файлов

### Архитектурные решения v0.2:

- ID файла = projectName + fileName (стабильный, уникальный)
- contentHash = MD5 содержимого (для отслеживания изменений)
- Сравнение БД, не переписывание (сохранение данных)
- История файлов в массиве events
- Мягкое удаление (deleted: true) вместо физического удаления

#### 2. ⚠️ ПРОБЛЕМЫ TELEGRAM И РЕШЕНИЯ

**ПРОБЛЕМА 1: Duplicate messages (бесконечное получение одних и тех же сообщений)**
- **Причина:** Telegram возвращает непрочитанные сообщения в polling, а код не отслеживал messageId
- **Решение:** Добавить поле `messageId` в каждый заказ и проверять дубликаты через БД перед вставкой
- **Состояние:** ✅ РЕШЕНО (v0.7 patch 1)

**ПРОБЛЕМА 2: Offset tracking не работал**
- **Причина:** lastUpdateId отслеживался но offset в polling конфиге не применялся правильно
- **Решение:** Правильно использовать offset в Telegraf polling конфиге с lastUpdateId
- **Состояние:** ✅ РЕШЕНО

**ПРОБЛЕМА 3: Photos не скачивались**
- **Причина:** Функция downloadPhoto создавалась но код был слишком медленный
- **Решение:** Оптимизировать скачивание, использовать https.get для параллельного скачивания
- **Состояние:** ✅ РЕШЕНО но нужна дополнительная проверка

**ПРОБЛЕМА 4: Polling интервал слишком частый (5 сек)**
- **Причина:** Система нагружалась постоянным обращением к Telegram API
- **Решение:** Увеличить интервал до 10 минут (600000ms) по рекомендации пользователя
- **Состояние:** ✅ РЕШЕНО в v0.7 patch 2

#### 4. 📋 СИСТЕМА BACKUP'А (В ПЛАНИРОВАНИИ)

**Цель:** Защита от повторения инцидента

**Структура (планируется):**
```
data/backups/
├── backup_001.json           ← Циклический (перезаписывается)
├── backup_002.json
├── backup_003.json
├── backup_004.json
├── FINAL_v1.json             ← Ручные (НЕ перезаписываются)
├── FINAL_v2.json
├── FINAL_v3.json
└── metadata.json             ← Информация о backup'ах
```

**Две системы:**
1. **АВТОМАТИЧЕСКИЕ** - создаются перед критическими операциями
   - Перед синхром Telegram заказов
   - Перед изменением файлов
   - Перед удалением файлов
   
2. **РУЧНЫЕ FINAL** - создаются пользователем через UI
   - "Mark as FINAL" - сохранить текущее как стабильное
   - Никогда не перезаписываются
   - Используются для восстановления в критических ситуациях

**Планируемый UI:**
```
💾 Backup Manager
├─ 🔵 FINAL_v1 (2026-10-11 01:38)
│  └─ [Restore] [Make Active]
├─ backup_001 (2026-10-11 23:00)
│  └─ [Restore] [Mark as FINAL]
├─ backup_002 (...)
└─ [💾 Create Backup Now]
```
